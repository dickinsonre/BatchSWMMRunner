---
name: SWMM WASM build
description: How the in-browser SWMM engine was built with emscripten and how it is wired into the app
---

- EPA SWMM 5.2.4 solver sources (`swmm-source/src/solver/*.c`) compile cleanly with emscripten 3.1.51 (installed as system dependency `emscripten`).
- Emscripten cache in the Nix store is read-only: copy it to a writable dir and `export EM_CACHE=...` before first `emcc` run (first run builds libc, ~90s; SWMM compile ~19s).
- Output artifacts live in `client/public/wasm/` (swmm5.js glue with MODULARIZE=1, EXPORT_NAME=createSwmmModule + swmm5.wasm) so Vite serves them statically; a classic worker (`swmm-worker.js`, importScripts) runs simulations off the main thread.
- **Why:** rebuilding requires this recipe; background bash processes get killed in this environment, so run emcc synchronously.
- **How to apply:** if SWMM sources change or exports need extending, re-run emcc with the same flags (exported swmm_* functions plus FS/ccall/getValue/UTF8ToString runtime methods, ENVIRONMENT=web,worker).
- A second engine ("SWMM6", OpenSWMM fork, identical swmm_* API) is built the same way to `client/public/wasm6/` with EXPORT_NAME=createSwmm6Module; the shared worker lazily importScripts the right glue per run message.
- The app's `swmm6` browser engine is the refactored OpenSWMM 6 C++ engine (handle-based `swmm_engine_*` API). Build with `-fexceptions`; without it, runs abort after parsing. Export every worker call, especially `_swmm_get_last_error_msg`: omitting it lets successful runs pass but turns any solver error into Emscripten's opaque `undefined.apply` exception.
- The `wasm6dev` tier builds from the same repository's `develop` branch. Both branches now use cmake target `openswmm_engine`, static library `build-wasm/src/engine/libopenswmm.engine.a`, and require `-I include/openswmm/engine -I build-wasm/include` when linking the CLI.
- The SWMMBobSWMM6 fork lags upstream: FV routing (FLOW_ROUTING FV, ExplicitFvSolver) only exists in HydroCouple/openswmm.engine `swmm6_rel`/`develop`. For engine rebuilds, fetch the HydroCouple repo, not just the fork. Both wasm6 (rel) and wasm6dev (develop) now build from HydroCouple tips; the develop-branch cmake target is `openswmm_engine`, static lib at `build-wasm/src/engine/libopenswmm.engine.a`, and the same three WASM patches apply cleanly. Verify FV after rebuild: `.rpt` must show "Flow Routing Method ...... FV" (tests/engine6Fv.test.ts).
- Recheck WASM compatibility patches against each source snapshot rather than applying all historical patches blindly. **Why:** upstream incorporated PluginFactory Emscripten stubs and synchronous IOThread handling, while the duplicate legacy non-OpenMP fallback still required deduplication. The newer source also dereferenced incomplete 2-D options even with 2-D disabled. **How to apply:** verify upstream guards, retain one fallback definition, and test the explicitly no-2-D configuration; do not enable 2-D merely to bypass compilation.
- Treat each OpenSWMM artifact's recorded source snapshot as its license authority; nearby branches/releases can use different licenses and NOTICE policies. **Why:** `swmm6_rel` was Apache-2.0 with NOTICE while the bundled `develop` snapshot was MIT with no NOTICE. **How to apply:** pin legal files to the exact commit, and preserve the final linker command/map on every rebuild so runtime-license inventory is reproducible rather than inferred.
